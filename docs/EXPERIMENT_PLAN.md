# 1. PURPOSE

This document defines the complete experimentation strategy for Project 3.

The purpose is to ensure that model development is performed through:

- Controlled experiments
- Reproducible configurations
- Valid train/validation separation
- Leakage prevention
- Consistent evaluation
- Explicit baselines
- Model comparison
- Ablation studies
- Cold-start analysis
- User-segment analysis
- Error analysis

The project shall not select or present a recommendation model merely because it appears sophisticated.

Model decisions must be supported by measurable evidence.

---

# 2. EXPERIMENTATION PHILOSOPHY

The experimentation process follows:

```text
Research Question
       ↓
Hypothesis
       ↓
Controlled Experiment
       ↓
Evaluation
       ↓
Error Analysis
       ↓
Interpretation
       ↓
Decision
       ↓
Documented Evidence
````

The project shall distinguish between:

### Observation

What the experiment actually measured.

### Interpretation

What the measured result may indicate.

### Hypothesis

What we expected before running the experiment.

### Decision

What implementation choice follows from the evidence.

The project must not turn an interpretation into a fact without supporting evidence.

---

# 3. EXPERIMENTATION PRINCIPLES

## EXP-PRINCIPLE-001 — Reproducibility

Every important experiment must be reproducible.

The experiment record should contain:

* Dataset/source version
* Data preprocessing version
* Split configuration
* Model
* Hyperparameters
* Random seed
* K values
* Evaluation metrics
* Runtime information where relevant
* Result artifact location

---

## EXP-PRINCIPLE-002 — Common Evaluation Protocol

Models being compared should use the same evaluation protocol wherever technically appropriate.

Differences in:

* Data split
* Candidate set
* Relevance definition
* K
* Filtering

can make model comparisons misleading.

---

## EXP-PRINCIPLE-003 — Baseline First

A simple baseline must be established before evaluating more complex models.

The primary baseline is:

> Popularity-Based Recommendation

---

## EXP-PRINCIPLE-004 — No Fabricated Results

No experiment may contain:

* Fabricated metrics
* Estimated metrics presented as measured results
* Placeholder values in final reports
* Manually adjusted scores
* Results copied from external examples

---

## EXP-PRINCIPLE-005 — No Fabricated Temporal Data

Experiments must not create artificial timestamps solely to satisfy the temporal validation requirement.

If a legitimate timestamp-bearing source cannot be obtained, the limitation must be documented.

---

## EXP-PRINCIPLE-006 — No Fabricated Behavioral Events

Experiments must not convert ratings into views/clicks/carts/purchases and present them as actual source events.

Any derived proxy must be explicitly identified as derived.

---

## EXP-PRINCIPLE-007 — Actual Recommendation Engine Evaluation

The final evaluation must evaluate actual recommendation outputs generated by the project's recommendation components.

A separate toy heuristic must not be presented as evaluation of the final system.

---

## EXP-PRINCIPLE-008 — Leakage Prevention

No information from the validation/test period may influence model training or evaluation features.

---

## EXP-PRINCIPLE-009 — Controlled Changes

When possible, one major experimental variable should be changed at a time.

---

## EXP-PRINCIPLE-010 — Evidence Before Selection

A model should only become the final candidate after its behavior has been evaluated and documented.

# 7. DATA EXPERIMENTS

# DATA-EXP-001 — Dataset Integrity Experiment

## Objective

Verify that the dataset used for experimentation is complete, structurally valid, and consistent with the documented data strategy.

## Questions

* Are required files present?
* Are required columns present?
* Are identifiers valid?
* Are interaction values valid?
* Are duplicates present?
* Are missing values present?
* Is product metadata available?

## Procedure

1. Load source data.
2. Validate file availability.
3. Validate schema.
4. Inspect data types.
5. Calculate missing-value statistics.
6. Calculate duplicate statistics.
7. Validate identifiers.
8. Generate a data audit report.

## Outputs

```text
Dataset row count
Column count
Missing-value report
Duplicate report
Unique users
Unique products
Interaction count
```

## Success Criteria

No unexplained structural problems remain.

# 9. DATA-EXP-003 — Timestamp Availability Investigation

## Objective

Determine whether a legitimate timestamp-bearing version/source corresponding to the project dataset exists.

## Critical Rule

No synthetic timestamps shall be created.

## Investigation Steps

1. Identify current dataset provenance.
2. Identify original dataset/project source.
3. Inspect official dataset documentation.
4. Identify historical versions.
5. Search for timestamp-bearing variants.
6. Verify whether the candidate source corresponds to the same underlying data/domain.
7. Compare:

   * User IDs
   * Product IDs
   * Interaction semantics
   * Dataset scope
   * Metadata
8. Determine whether timestamp restoration is legitimate.

## Possible Outcomes

### Outcome A

A legitimate corresponding timestamp-bearing source is found.

Proceed with temporal validation.

### Outcome B

No legitimate timestamp-bearing source is found.

Document:

* Evidence
* Limitation
* Impact
* Alternative evaluation methodology

Do not fabricate chronology.

# 12. BASELINE EXPERIMENTS

# BASE-EXP-001 — Popularity Baseline

## Objective

Establish a simple non-personalized benchmark.

## Hypothesis

A popularity-based model should provide a meaningful reference point but will not personalize recommendations to individual users.

## Procedure

1. Calculate popularity from training data only.
2. Rank products.
3. Exclude invalid/unavailable products.
4. Generate Top-K recommendations.
5. Evaluate using the standard metrics.

## Metrics

* Precision@K
* Recall@K
* NDCG@K

## Required Output

| Model      |  K | Precision@K | Recall@K |   NDCG@K |
| ---------- | -: | ----------: | -------: | -------: |
| Popularity |  K |    measured | measured | measured |

Actual values must be populated only after execution.

---

* Coverage

# 68. EXPERIMENT STOPPING RULES

An experiment may be stopped when:

1. It clearly demonstrates the relevant behavior.
2. Additional configurations are unlikely to change the engineering decision.
3. Computational cost becomes disproportionate.
4. A prerequisite is shown to be invalid.
5. The experiment becomes methodologically invalid.

The stopping reason should be documented.

---

# 69. NEGATIVE RESULTS POLICY

Negative results are valid project results.

Examples:

```text
Collaborative filtering does not outperform popularity.
```

or:

```text
Increasing latent dimensions does not improve NDCG.
```

or:

```text
Content-based recommendations provide poor relevance because metadata is insufficient.
```

Such results must not be hidden.

The project should explain possible reasons and implications.

---

# 70. NO RESULT MANIPULATION POLICY

The following are prohibited:

* Changing the split after seeing results solely to improve scores.
* Removing difficult users without justification.
* Removing poor-performing items without methodological justification.
* Reporting only the best K.
* Reporting only the best experiment.
* Changing relevance thresholds after seeing results without documenting the change.
* Selecting a model before evaluation and then designing experiments to justify it.

# 75. FINAL EXPERIMENTATION STANDARD

The purpose of experimentation in Project 3 is not to obtain the highest possible metric by any means.

The purpose is to establish a scientifically and technically defensible answer to:

> **Which recommendation approach provides useful, reproducible, and appropriately evaluated personalized product recommendations under the constraints and characteristics of the available data?**

Therefore:

```text
Valid Data
    ↓
Controlled Experiment
    ↓
Fair Comparison
    ↓
Leakage Prevention
    ↓
Measured Metrics
    ↓
Error Analysis
    ↓
Evidence-Based Decision
```

The project shall prefer:

```text
Honest Negative Result
        >
Fabricated Positive Result

Valid Evaluation
        >
Convenient Evaluation

Real Timestamp
        >
Invented Timestamp

Actual User Behavior
        >
Fabricated Events

Canonical Model
        >
Duplicated Logic

Reproducible Experiment
        >
One-Time Experiment
```

# 76. FINAL EXPERIMENT PLAN STATEMENT

`EXPERIMENT_PLAN.md` establishes the experimentation framework for the Personalized Product Recommendation Model.

The experimentation process shall systematically progress from:

```text
Data Understanding
        ↓
Data Validation
        ↓
Baseline
        ↓
Personalized Models
        ↓
Content-Based Model
        ↓
Cold-Start
        ↓
Hybrid Recommendation
        ↓
Ablation
        ↓
Temporal Evaluation
        ↓
Segment Analysis
        ↓
Error Analysis
        ↓
System Validation
        ↓
Reproducibility
        ↓
Final Model Decision
```

No final model, metric, experiment, or technical conclusion shall be considered valid unless it is supported by actual execution and documented evidence.

The final objective is not merely to demonstrate that a recommendation algorithm can generate a list of products.

The objective is to demonstrate that the complete recommendation system:

* Uses legitimate data.
* Represents interactions correctly.
* Generates meaningful recommendations.
* Handles cold-start conditions.
* Prevents leakage.
* Uses appropriate ranking metrics.
* Evaluates recommendations fairly.
* Provides meaningful segment analysis.
* Integrates into a coherent application.
* Produces reproducible results.
* Can be technically explained and defended.
